# PKMOBA 1v1 对战系统方案

- 方案版本：1.0
- 适用版本：PKMOBA 0.27.x 后续版本
- 目标平台：Minecraft 1.21.1 + Fabric + Cobblemon 1.8.2
- 状态：设计方案，尚未实现

## 1. 目标与边界

PKMOBA 当前是单人上帝视角训练/操控模式。本方案新增一个独立的 1v1 对战层：两名玩家各控制一只宝可梦，在同一竞技场内实时战斗，先击败对方获得胜利。

保留现有能力：

- 服务端权威判定伤害、技能、移动和胜负。
- 继续使用 Q/W/E/R、技能点、冷却、真实实体生命值。
- 继续使用 Cobblemon 的 PokemonEntity、模型、动画、声音和资源。
- 喷火龙、水箭龟作为首批可选宝可梦。
- 单人 `/mo summon` 训练模式继续可用，不强制进入对战。

本阶段明确不做：跨服务器匹配、排位分数、经济装备、兵线基地、3v3、AI 队友、观战回放。

## 2. 对局规则

### 2.1 基本规则

- 人数：2 名玩家，1 对 1。
- 每名玩家：1 只宝可梦，一命制。
- 默认模式：击败对方宝可梦即胜利。
- 玩家本体不参与伤害和胜负；玩家退出、死亡或断线时对局按离场规则处理。
- 友伤关闭；只能伤害对手宝可梦及允许的训练目标。
- 对局默认限时 10 分钟。
- 时间结束时，按宝可梦当前生命百分比判定；百分比相同则平局。
- 平局不复活、不补发奖励，记录为 Draw。

### 2.2 对局阶段

```text
IDLE
  -> INVITE_PENDING
  -> ROOM_READY
  -> COUNTDOWN
  -> FIGHTING
  -> FINISHING
  -> RESULT
  -> IDLE
```

规则：

- `IDLE`：玩家不在对局中，可训练、召唤或发起挑战。
- `INVITE_PENDING`：挑战邀请有效 30 秒；被邀请者只能接受或拒绝。
- `ROOM_READY`：双方确认，锁定宝可梦种类和竞技场位置。
- `COUNTDOWN`：5、4、3、2、1、FIGHT；禁止伤害、技能和移动。
- `FIGHTING`：正常战斗，开始计时。
- `FINISHING`：已确定结果，停止技能、移动和伤害，播放短结算效果。
- `RESULT`：显示胜负、伤害、持续时间和退出按钮，持续 8 秒后清理。

### 2.3 默认数值

| 项目 | 初始值 |
| --- | ---: |
| 竞技场形状 | 圆形 |
| 竞技场半径 | 24 格 |
| 双方出生距离 | 32 格 |
| 对局限时 | 600 秒 |
| 倒计时 | 5 秒 |
| 结算展示 | 8 秒 |
| 离场宽限 | 15 秒 |
| 安全边界 | 圆心外 24 格 |
| 边界处理 | 软推回，不造成伤害 |

竞技场应使用专用空旷区域或预先标记的对战场地，不能依赖任意玩家当前位置作为长期竞技场。首版可以由管理员使用 `/mo duel create` 在当前位置创建临时竞技场。

## 3. 房间与指令

首版采用指令开房，避免先实现匹配队列：

```text
/mo duel challenge <玩家>
/mo duel accept <玩家>
/mo duel deny <玩家>
/mo duel leave
/mo duel spectate <对局ID>       # 后置，不在首版实现
/mo duel status
/mo duel arena create <半径>
/mo duel arena remove
```

指令约束：

- 发起者和被邀请者必须在线、在同一维度、未处于其他对局。
- 双方距离不得超过 64 格，或由管理员创建固定竞技场后不限制距离。
- 对局创建时锁定双方的宝可梦种类；战斗中禁止 `/mo summon`、`/mo remove` 和切换控制对象。
- `/mo duel leave` 在战斗中视为投降；断线超过 15 秒视为投降。
- 管理员可执行 `/mo duel cancel <对局ID>` 强制结束异常房间。

## 4. 双方实体与归属

当前代码使用全局单实体/静态技能状态，不能直接扩展成多人对战。1v1 必须改为按 `MatchId` 或玩家 UUID 隔离：

```text
DuelMatch
- matchId
- dimension
- arenaCenter
- arenaRadius
- phase
- phaseTicks
- playerA UUID
- playerB UUID
- pokemonA entity UUID / entity ID
- pokemonB entity UUID / entity ID
- startTick
- endReason
```

每只宝可梦必须有明确归属：

```text
PokemonCombatOwner
- matchId
- owner UUID
- teamSlot A or B
```

所有 C2S 请求都必须由服务端从玩家 UUID 反查实体，禁止客户端提交任意 entityId 作为控制对象。服务端必须同时检查：

1. 玩家确实属于该对局。
2. 当前阶段是 `FIGHTING`，或请求属于倒计时允许项。
3. 提交的实体是该玩家在该对局中的实体。
4. 实体 UUID、维度、距离、生命状态均有效。
5. 技能、目标点、方向、位移速度在服务端限制内。
6. 伤害目标属于对手阵营，不能伤害自己、己方实体或其他对局实体。

## 5. 生命与胜负

### 5.1 生命处理

继续使用 Minecraft 世界实体生命作为显示和受伤入口，但对局层负责监听死亡：

```text
onPokemonHurt(match, source, target, amount)
  校验 source/target 属于同一对局且阵营相反
  交给 CombatDamage.apply
  广播伤害数字与受击反馈

onPokemonDeath(match, deadPokemon)
  锁定 FINISHING
  winner = opponent(deadPokemon.owner)
  停止所有技能、移动、粒子和导航
  广播 DuelEndPayload
```

死亡不可复活。实体可以在结算结束后移除，不能把普通世界中的其他 Cobblemon 宝可梦误判为对局实体。

### 5.2 断线与投降

- 倒计时前断线：房间取消，不判胜负。
- 战斗中断线：进入 15 秒宽限，实体暂时冻结并显示“对手重新连接中”。
- 超过宽限仍未回来：断线方判负。
- 主动 `/mo duel leave`：立即投降。
- 服务器重启：首版直接取消未结算对局，双方不判胜负；后续再做持久化恢复。

## 6. 竞技场

首版竞技场由服务端保存，不依赖客户端坐标：

- 圆心、半径、维度属于 `DuelMatch`。
- 双方宝可梦限制在圆形边界内。
- 目标点、E 位移终点、投射物和范围技能都必须经过场地截断。
- 超出边界的宝可梦每 tick 被软推回；不使用伤害惩罚，避免网络抖动造成误杀。
- 竞技场中心和周边区块在对局期间强制加载。
- 非对局实体不能进入伤害筛选，避免野生生物或第三方玩家干扰。
- 方块破坏、放置、流体变化、爆炸在竞技场内禁止；对局结束后恢复玩家权限。

建议首版使用空旷平面地图，不加入高低差、可破坏掩体和特殊地形。等基础判定稳定后再增加障碍物。

## 7. 技能兼容规则

### 喷火龙

- Q/W/E/R 保持当前技能行为。
- E 期间禁止 R，已实现的限制继续保留。
- Q 的显示和判伤继续共用服务端原点、方向、墙体截断和 3D 扇区。
- 所有技能目标过滤改为“同一 DuelMatch 且对方阵营”。

### 水箭龟

- Q/W/E/R 保持当前实现。
- E 期间禁止 R。
- 普攻 4 格和水泡/炮口水雾属于表现与基础攻击规则，不因进入对局改变。
- 两个炮口水柱、Q 水刃、W 水球、E 旋转均必须带 `matchId` 或实体归属校验。

### 技能状态隔离

当前 `CharizardCombat`、`BlastoiseCombat` 中的静态 channel、points、cooldown、aim 等状态必须从“全局一份”改为：

```text
Map<UUID, CombatState> statesByPokemon;
```

或直接挂在 `DuelMatch` 的双方状态中。单人训练模式可以使用独立的 `TrainingCombatState`，不能与对局状态共用冷却和技能点。

## 8. 网络协议

建议新增以下 payload：

### 客户端到服务端

- `DuelInvitePayload(targetUuid)`：发起挑战。
- `DuelResponsePayload(inviterUuid, accepted)`：接受/拒绝。
- `DuelReadyPayload(ready)`：双方准备确认。
- `DuelSurrenderPayload()`：投降。
- `DuelRequestStatePayload()`：请求重新同步对局状态。

### 服务端到客户端

- `DuelInvitePayload`：显示邀请弹窗。
- `DuelRoomPayload(matchId, phase, players, species)`：房间和阶段。
- `DuelCountdownPayload(remainingTicks)`：倒计时。
- `DuelArenaPayload(center, radius, dimension)`：竞技场边界。
- `DuelStatePayload(...)`：双方实体、生命、技能点、CD、剩余时间。
- `DuelDamagePayload(targetId, amount, position)`：伤害数字。
- `DuelEndPayload(winnerUuid, reason, duration)`：结算。

所有服务端到客户端状态包应带 `matchId` 和递增 `stateRevision`。客户端丢包后只显示旧状态，收到更小 revision 的包必须丢弃；重新进入视距或重连时请求完整同步。

## 9. UI

### 房间阶段

- 屏幕中央：挑战邀请、接受/拒绝按钮。
- 顶部：双方名称、宝可梦图标、当前生命百分比。
- 中央：5 秒倒计时和 `FIGHT`。
- 顶部中间：对局计时器。

### 战斗阶段

保留现有底部技能栏，在其上增加：

- 对手血条和宝可梦名称。
- 自己/对手的生命数字。
- 圆形竞技场边界提示。
- 当前状态：倒计时、战斗中、对手重连、结算。
- E 期间 R 图标置灰，并用短提示说明“飞行中不可使用”。

### 结算阶段

显示：

- 胜利、失败或平局。
- 胜者和结束原因：击败、投降、断线、超时。
- 对局持续时间。
- 双方造成伤害和承受伤害。
- “返回训练场”按钮。

UI 只显示客户端已经收到的状态，不能由客户端自行决定胜负、扣血或技能可用性。

## 10. 平衡建议

第一版不做复杂属性克制，但需要避免两只宝可梦的基础规则不一致：

- 双方最大生命、技能点上限和回复规则应在对局配置中明确，而不是从全局静态变量读取。
- 所有技能伤害先沿用当前值，建立对局统计后再调数值。
- 记录每局 Q/W/E/R 命中次数、伤害、使用次数、平均存活时间。
- 水箭龟的 E 旋转不能因为视觉姿态改变碰撞盒；判定始终使用服务端实体 AABB。
- 不添加属性克制，直到两套技能的射程、伤害和冷却有真实数据。

## 11. 分阶段实施

### M1：单服务器双人房间骨架

- `DuelMatch`、阶段状态机、邀请/接受/拒绝。
- `/mo duel` 指令。
- 两名玩家加入同一临时竞技场。
- 倒计时、离场、清理。
- 暂时只允许管理员或同局内直接召唤。

验收：两个玩家能创建房间、看到倒计时，取消或离开后双方恢复正常状态。

### M2：双实体与归属

- 每名玩家一只宝可梦。
- 去掉全局唯一实体假设，改为按 match/player 保存。
- 所有移动、技能、瞄准、同步请求做 owner 和 match 校验。
- 单人训练模式与 DuelMatch 状态隔离。

验收：A 不能控制 B 的宝可梦；两局同时存在时状态互不串线。

### M3：战斗与胜负

- 对手目标过滤。
- 真实伤害、死亡监听、一命制。
- E 期间禁 R、CD、技能点按双方独立运行。
- 胜负、投降、断线宽限、超时。

验收：击杀、投降、断线和超时各有正确结果；结算后实体和权限清理干净。

### M4：UI 与异常恢复

- 双方血条、计时器、倒计时、结算面板。
- 断线重连全量同步。
- 服务器强制取消和异常清理。
- 训练木桩和对局统计接口。

验收：客户端重连、丢包、跨区块和服务器取消不留下锁定玩家或残留实体。

### M5：体验与扩展

- 固定竞技场模板。
- 观战、地图选择、更多宝可梦。
- 对局记录和简单胜负统计。
- 后续再评估匹配和排位。

## 12. 关键风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 当前战斗状态是静态全局变量 | 两玩家串技能、串 CD | 改为按对局/实体 UUID 存储 |
| 当前控制对象偏向全局 active entity | 玩家可控制他人实体 | 所有请求由玩家 UUID 反查并校验 owner |
| Cobblemon 原生 AI 与对局移动竞争 | 实体抖动、脱离边界 | 对局实体统一由 DuelCombat 驱动，或显式停用相关 AI |
| 普通世界伤害混入对局 | 非法击杀 | 对局伤害入口统一白名单，并记录 source/target |
| 客户端只做表现 | 显示与服务端状态短暂不同 | matchId + revision，全量同步接口 |
| 服务器重启 | 残留实体和锁定 | 首版取消全部对局并扫描清理带 match tag 的实体 |
| 旧单人模式回归 | 当前功能被破坏 | 保留 TrainingMatch/训练分支，先写单元式状态测试再接 UI |

## 13. 推荐首个可玩切片

第一版不要同时做匹配、观战和排位。推荐交付顺序：

1. `/mo duel challenge <玩家>` 和接受/拒绝。
2. 固定圆形竞技场，双方各一只已选宝可梦。
3. 5 秒倒计时后进入战斗。
4. 双方独立 Q/W/E/R、技能点、冷却和真实 HP。
5. 一方死亡、投降或断线后结算。
6. 结算清理并恢复玩家操作。

这个切片完成后，才有必要加入正式匹配和长期战绩。

## 0. 一句话路线

不自定义实体、不自定义渲染器 —— 直接用 Cobblemon 的 `Pokemon.sendOut()` 生成一只真正的 `PokemonEntity`（species = charizard），
模型/贴图/动画全部由 Cobblemon 白送；我们只做三件事：
**① 服务端生成并记住这只实体；② `Camera.setup` 里改位置做上帝视角；③ 客户端右键发自定义包，服务端每 tick 把这只实体往目标点推。**

## 1. 怎么用代码生成一只指定物种的宝可梦

### 1.1 入口：`Pokemon.sendOut(...)`

**【源码】** `common/src/main/kotlin/com/cobblemon/mod/common/pokemon/Pokemon.kt:799-813`

```kotlin
fun sendOut(level: ServerLevel, position: Vec3, illusion: IllusionEffect?, mutation: (PokemonEntity) -> Unit = {}): PokemonEntity? {
    CobblemonEvents.POKEMON_SENT_PRE.postThen(PokemonSentEvent.Pre(this, level, position)) {
        SeasonFeatureHandler.updateSeason(this, level, position.toBlockPos())
        val entity = PokemonEntity(level, this)          // ← 实体就在这里被造出来
        illusion?.start(entity)
        val adjustedPosition = entity.getAdjustedSendoutPosition(position)
        entity.setPositionSafely(adjustedPosition)
        mutation(entity)                                  // ← 我们唯一能插手的回调
        entity.finalizeSpawn(level, level.getCurrentDifficultyAt(...), MobSpawnType.EVENT, null)
        level.addFreshEntity(entity)
        state = SentOutState(entity)
        return entity
    }
    return null
}
```

关键点：
- `PokemonEntity(level, pokemon)` 的构造签名是 `(world, pokemon, type = CobblemonEntities.POKEMON)`——**【源码】** `entity/pokemon/PokemonEntity.kt:186-190`。**它不用自定义 EntityType，所以不需要注册实体类型**。
- `sendOut` 会走 `POKEMON_SENT_PRE` 事件；**若事件被取消，函数返回 `null` 且什么都不会生成**（`postThen` 语义）。**【源码】** 同上。
- `mutation` 回调拿到的是**已经摆好位置、还没进世界**的实体，是设置 owner / isNoAi / 自定义 NBT 的正确时机。**【源码】**
- 没有战斗时更省事的封装是 `sendOutWithAnimation(...)`（`Pokemon.kt:815`），它在 885 行做了 `it.ownerUUID = getOwnerUUID()`，并且会播放出场动画；但它需要一个 `LivingEntity source` 与 `getOwnerUUID()` 非空（否则 owner 为 null）。**【源码】** `Pokemon.kt:838-890`

### 1.2 需要哪些字段

| 字段 | 怎么设 | 依据 |
|---|---|---|
| `species` | **必须**用 `PokemonSpecies.getByIdentifier(...)` 取得已注册的 Species 再赋值。`species` 的 setter 里有硬校验：`if (PokemonSpecies.getByIdentifier(value.resourceIdentifier) == null) throw IllegalArgumentException` | 【源码】`Pokemon.kt:183-187` |
| `uuid` | 自动 `UUID.randomUUID()`，**一般不要手动改** | 【源码】`Pokemon.kt:182` |
| `level` | `pokemon.level = 50`（默认 1） | 【源码】`Pokemon.kt:320` |
| owner | 优先让 pokemon 进入玩家的 party/PC（`storeCoordinates`），`getOwnerUUID()` 从 store 取；否则退而求其次，在 mutation 里直接给**实体**设 `entity.ownerUUID = player.uuid` | 【源码】`Pokemon.kt:1537-1572`；`Pokemon.kt:885` 演示了给实体设 ownerUUID 的做法 |
| `tethering` | 若希望它"一直跟着玩家、被召回"，Cobblemon 用 `tetheringId` / `tethering`；不设也能正常存在 | 【源码】`Pokemon.kt:526`、`PokemonEntity.kt:715-732` |
| party 归属 | 代码里最稳的是把这只 pokemon 放进玩家队伍（`Cobblemon.storage.getParty(player)`），这样 owner/persistence/召回全通 | 【未知】具体 party API 的准确方法名本轮未逐行核对 |

### 1.3 charizard 的 species 标识怎么写

Cobblemon 的 species 以 `ResourceLocation("cobblemon", "<name>")` 标识，喷火龙是 `charizard`（小写、无前缀）。
**【推断】** 依据：species setter 用 `value.resourceIdentifier` 查注册表，而全部原版宝可梦资源都挂在 `cobblemon` 命名空间（例如 datapack `data/cobblemon/species/charizard.json`——本轮只确认了目录约定，未打开该 json）。

推荐写法（Kotlin，**可直接照抄，注意这是推断出来的 API 用法**）：

```kotlin
val species = PokemonSpecies.getByIdentifier(ResourceLocation.fromNamespaceAndPath("cobblemon", "charizard"))
    ?: error("charizard not registered")
val pokemon = Pokemon().apply {
    isClient = false            // 服务端创建；客户端创建的 Pokemon 必须 isClient = true
    this.species = species      // 必须在 isClient 之后？不必须，但 setter 内会走 onChange 发包
    level = 50
}
val entity = pokemon.sendOut(serverLevel, targetPos, null) { e ->
    e.ownerUUID = player.uuid
    e.isNoAi = true             // 见第 4 节
}
```
**【未知/需验证】** `isClient` 的赋值顺序与 `Pokemon()` 无参构造后 `onChange` 是否会在 `isClient=false` 时尝试发包（`Pokemon.kt:181-205` 的 setter 会 `onChange(SpeciesUpdatePacket(...))`）。**第一次跑通前建议先试"构造 → 设 species → 设 level → sendOut"，若日志报 `Cobblemon.network` 相关空指针，就改成先 `isClient = true` 再翻转**。

## 2. 渲染是不是白送？

**是白送，前提是你用的是 Cobblemon 自己的 `PokemonEntity`。**

**【源码】**
- `common/.../client/CobblemonClient.kt:579`：
  `this.implementation.registerEntityRenderer(CobblemonEntities.POKEMON, ::PokemonRenderer)`
  → **全局只注册了一次**，类型是 `CobblemonEntities.POKEMON`，不是按物种注册。
- `client/render/pokemon/PokemonRenderer.kt:69` 定义 `class PokemonRenderer(...)`，`:99` 是 `override fun render(...)`。
- `PokemonEntity` 的默认 type 就是 `CobblemonEntities.POKEMON`（`PokemonEntity.kt:189`）。

结论：
1. **不要去注册 renderer**。我们自己 mod 里若再 `EntityRendererRegistry.register(CobblemonEntities.POKEMON, ...)` 会覆盖/冲突，属于找死。
2. 模型、贴图、异色、火焰帧、叫声都在 Cobblemon 的资源包里，随依赖 mod 加载。
3. 客户端侧只要 Cobblemon 正常加载，`sendOut` 之后客户端会收到实体生成包并自动按 `entity.pokemon.species` 选模型（具体按 species 分发的那段在 `PokemonRenderer` 内部，本轮未逐行读完 → **【推断】** 分发依据为实体同步过来的 species）。

> 因此：**M0.5 的"看到喷火龙"不依赖我们写任何渲染代码**。风险只在于"服务端生成了但客户端看不到"（实体未同步/被立刻移除），不是渲染注册问题。

## 3. 动画怎么驱动

### 3.1 结论

**不需要我们驱动。** 动画由客户端 `PosableModel` 的 pose 系统按模型里的命名 clip 播放，而 pose 的选择由 Cobblemon 自己的 `PokemonEntity` 状态驱动。

**【源码】证据**
- pose 名是**字符串约定**，写在各宝可梦模型类里：
  - `client/render/models/blockbench/pokemon/gen7/DartrixModel.kt:86` → `poseName = "fly"`，`:104` → `poseName = "walk"`
  - `client/render/models/blockbench/pokemon/gen3/ExploudModel.kt:45` → `bedrock("exploud", "idle")`（idle 是基础 clip 名）
  - 全库同类写法大量存在（grep `poseName = "walk"` 命中 100+ 个模型）
- 实体状态字段：`PokemonEntity.kt:197` 的 `MOVING`（同步数据），以及 `:653-654`
  ```kotlin
  isPokemonFlying = flyDist - flyDistO > 0.005F
  isPokemonWalking = walkDist - walkDistO > 0.005F
  ```
  → **walk / fly 是由"本 tick 是否真的在走 / 在飞"自动判定的**，我们只要让实体真的移动，动画自己会切。

### 3.2 名字汇总

| 语义 | pose/clip 名 | 依据 |
|---|---|---|
| idle | `idle` | 【源码】ExploudModel.kt:45 等 |
| 走路 | `walk` | 【源码】DartrixModel.kt:104 等 |
| 飞行 | `fly` | 【源码】DartrixModel.kt:86 等 |

**【未知】** 喷火龙模型类本轮**没找到** `CharizardModel.kt`（`gen1` 目录下不存在该文件），因此喷火龙具体注册了哪些 pose 名、是否有专属 `flap`/`air` 之类，**未确认**。但按上表通用约定，`walk` / `fly` / `idle` 覆盖 95% 物种，先按这三个做。

### 3.3 实操建议

- 想让它在天上飞：**不要**只设 `isNoAi`——要让 `flyDist` 增长（真正在空中移动），否则 `isPokemonFlying=false`，播的是 walk。
- 如果出现"在滑但不动腿"，那是 `walkDist` 没增长：说明我们改的是 `setDeltaMovement` 但实体没真正 `move()` —— 见第 4 节，**必须调用 `entity.move(MoverType.SELF, vec)` 才会累加 walkDist**（**【推断】**，需实机验证）。

## 4. 怎么让它听指挥走

### 4.1 `isNoAi = true` 到底关了什么

- `isNoAi()` 是 **`Mob`** 的同步标志位（NBT 键 `NoAI`，见反编译符号：`Mob.addAdditionalSaveData` / `readAdditionalSaveData` 里读写 `NoAI`）。**【源码·反编译】** 本轮用 `javap -c` 查看了 `net.minecraft.world.entity.Mob`，确认有 `isNoAi()` 与 `NoAI` 字符串的存取。
- `PokemonEntity` 本身**没有**覆盖 `aiStep()`，只覆盖了 `tick()`（`PokemonEntity.kt:639`，其中 `:651` 调 `super.tick()`）和 `travel()`（`:1913`）。**【源码】**
- `LivingEntity.aiStep()` 会调用 `serverAiStep()`（`javap` 确认：`LivingEntity.aiStep` 字节码第 287 行 `invokevirtual serverAiStep:()V`），而 `serverAiStep()` 才是 **goalSelector / navigation / sensing 的 tick 入口**（**【推断】** 这是 1.21 的通行结构，本轮未在 `Mob.serverAiStep` 里逐行定位 `isNoAi` 判断）。

**定论（收窄）**：
- 【源码】物理/重力/碰撞不在 `serverAiStep` 里，`isNoAi=true` **不会让实体悬浮或免疫重力**。
- 【推断】`isNoAi=true` 会停掉 goalSelector（所以不会乱跑、不会打玩家）并且**大概率**连带停掉 `navigation.tick()`——这正是"设了 NoAI 之后 `getNavigation().moveTo()` 看似没反应"的最常见原因。
- **【未知】** 未实机确认 `isNoAi=true` 时 `navigation.moveTo` 是否完全失效。**不要把它当既定事实**，按下面的推荐路线绕开这个问题。

### 4.2 推荐路线（最省事、最不依赖 Cobblemon 内部状态）

> **服务端每 tick 直接位移 + 转向，不用 navigation。**

理由：
1. `isNoAi=true` 关掉野生 AI，避免它自己跑去打怪/乱走，这是必须的；
2. navigation 在 NoAI 下的行为有不确定性（上面【未知】），而"每 tick 直接推"是**完全受控**的，不受 AI 状态影响；
3. 我们后面要做技能位移（E 飞行、R 蓄力），本来就不能依赖寻路。

伪代码（**服务端**，`ServerTickEvents.END_LEVEL_TICK` 或自建 entity tick 回调）：

```kotlin
val to = target.subtract(entity.position())
val flat = Vec3(to.x, 0.0, to.z)
if (flat.length() < 0.35) return
val dir = flat.normalize()
val speed = 0.25                 // 格/tick = 5 格/秒（任务书要求）
entity.deltaMovement = Vec3(dir.x * speed, entity.deltaMovement.y, dir.z * speed)
entity.hurtMarked = true          // 让客户端接受速度覆盖（很关键）
entity.yRot = (Math.toDegrees(atan2(dir.z, dir.x)) - 90.0).toFloat()
entity.yBodyRot = entity.yRot
entity.yHeadRot = entity.yRot
```
**【推断】** `hurtMarked = true` 是 1.21 里让服务端速度变更同步到客户端的常用手段（不是专门给伤害用的）；不设的话客户端可能仍按旧速度渲染，出现"橡皮筋"。
**必须同时设 `yBodyRot` 和 `yHeadRot`**，只设 `yRot` 在 Cobblemon 的 `tick()` 里会被角度归一化逻辑覆盖（`PokemonEntity.kt:641-648` 会 wrap 这些角）。

是否用 `entity.move(MoverType.SELF, delta)` 而不是 `setDeltaMovement`：
- 想播 **walk 动画**：优先 `move()`，因为 `walkDist` 由 `Entity.move()` 累加（**【推断】**）。
- 想跳/飞：`setDeltaMovement` + `move` 组合。

**降级方案**（如果上面被 Cobblemon 的 `travel()` 覆盖 —— `PokemonEntity.kt:1913` 有自定义 `travel`）：
先用 `entity.isNoAi = false` + 自定义 `Goal`（`goalSelector.addGoal(0, ...)` 优先级最高），在 goal 里调 `entity.navigation.moveTo(x,y,z,speed)`，并每 tick 检查 `navigation.isDone`。这条路更"正统"但代码量翻倍，**只在 4.2 实测失败时启用**。

## 5. 我们自己的 Fabric 模组怎么加 mixin

### 5.1 Cobblemon 自己是怎么注册的（参考样板）

**【源码】**
- `fabric/src/main/resources/fabric.mod.json` 的 `"mixins": ["mixins.cobblemon-common.json", "mixins.cobblemon-fabric.json"]`
- `common/src/main/resources/mixins.cobblemon-common.json:2-4`：`"package": "com.cobblemon.mod.common.mixin"`, `"compatibilityLevel": "JAVA_21"`, `"minVersion": "0.8"`
- `:9-47` 的 `"client"` 数组里第 23 行就是 `"client.CameraMixin"`；`:48` 起是 `"mixins"`（服务端也加载的）数组。
- `fabric/src/main/resources/mixins.cobblemon-fabric.json` 里 `"client": ["FabricCameraMixin", ...]`，并挂了 `"plugin": "com.cobblemon.mod.fabric.mixin.MixinConfigPlugin"`。
- 两个 json 里**都没有 `refmap` 字段**。**【源码】** —— 说明 Cobblemon 的 refmap 是构建期由 Loom/Architectury 注入的（生产 jar 里应该会带上）。**【推断】**：Loom 的 `mixin { add sourceSets.main, "cobblemon-common-refmap.json" }` 那种写法通常在 `build.gradle.kts` 里，而我在 `common/build.gradle.kts` 前 40 行没看到（本轮只读了开头，未读完 → **【未知】**）。

### 5.2 我们该怎么做

我们新建的 Fabric 模组标准三件套：

1. `src/main/resources/mymod.mixins.json`
   ```json
   {
     "required": true,
     "package": "com.example.mymod.mixin",
     "compatibilityLevel": "JAVA_21",
     "minVersion": "0.8",
     "refmap": "mymod.refmap.json",
     "client": ["CameraMixin"],
     "mixins": []
   }
   ```
2. `fabric.mod.json` 加 `"mixins": ["mymod.mixins.json"]`
3. **开发环境**：Loom 会处理 refmap（`loom { mixin { defaultRefmapName = "mymod.refmap.json" } }` 或 `mixin { add sourceSets.main, "mymod.refmap.json" }`）。**生产环境必须带 refmap**，否则混淆后注入失败。

关于 **`CameraMixin` 是 common 模块**这件事的结论：**不需要管 Cobblemon 的 mixin 放哪、也不需要"继承"它**。Mixin 是按目标类叠加的：
- Cobblemon 的 `client.CameraMixin` 已经 `@WrapOperation` 了 `Camera.setup` 里的 `setPosition(DDD)`（`CameraMixin.java:63-64`）；
- 我们**再写一个** `@Mixin(Camera.class)` 的 `@WrapOperation` 注入同一个点，是完全合法的，两个 wrap 会按优先级链式执行。**【推断】**（Mixin 的标准行为；未实机验证优先级顺序）。

**如果两者都想改最终位置，谁后执行谁说了算** —— 我们的 wrap 里若 **不调用 `original.call(...)` 直接 `setPosition(...)`**，就会完全接管（Cobblemon 那个 wrap 在非骑乘分支里最后也是 `original.call(...)`，见 `CameraMixin.java:87`，所以它的实现不会跟我们打架）。

## 6. 上帝视角镜头的最小改法

### 6.1 最少改一处

**【源码】** Cobblemon 的 `CameraMixin.java:63-64`：
```java
@WrapOperation(method = "setup", at = @At(value = "INVOKE",
    target = "Lnet/minecraft/client/Camera;setPosition(DDD)V"))
public void cobblemon$positionCamera(Camera instance, double x, double y, double z,
        Operation<Void> original, @Local(ordinal = 1, argsOnly = true) boolean thirdPersonReverse) {
```
并且 `:79-82` 证明：**直接用 `setPosition(position)` 覆盖、`return` 掉，不再调 `original`，是完全可行的**（骑乘时就是这么干的）。

我们照抄这个形状：

```java
@Mixin(Camera.class)
public abstract class GodCameraMixin {
    @Shadow protected abstract void setPosition(Vec3 pos);

    @WrapOperation(method = "setup", at = @At(value = "INVOKE",
        target = "Lnet/minecraft/client/Camera;setPosition(DDD)V"))
    private void mymod$godCamera(Camera self, double x, double y, double z,
                                 Operation<Void> original) {
        if (!GodMode.active()) { original.call(self, x, y, z); return; }
        setPosition(GodMode.cameraPos());
        // 不调 original → 位置完全由我们接管
    }
}
```
注意：`Camera.setup` 里**同时**会 `setRotation(yRot, xRot)`（朝向）——所以我们只覆盖 `setPosition`，**朝向继续跟着玩家/鼠标走，完全不受影响**。这正是你要的"只改位置不改朝向"。

### 6.2 只改位置行不行

**行。** 理由：`Camera` 的朝向由 `setRotation` 决定，而我们只替换了 `setPosition(DDD)` 这一处调用；镜头实体（`entity` 字段）也没动，所以：
- 鼠标转向、第一/第三人称、`F5` 都保持玩家原样；
- 玩家本人还在原地（第 6.3 的锁定是另一件事）；
- 方块加载/雾效跟随 `Camera` 位置，会自动生效。

**副作用（必读）**：
- **遮挡裁剪**：镜头位置离开玩家身体后，`Camera.setup` 里的 `setup` 后续逻辑（如 `getMaxZoom`、`isDetached`）**没有运行**，所以镜头可能穿进方块。M0.5 可以先忍（任务书允许 M0.5 不做碰撞），后续若穿墙明显，再加 `Minecraft.getCameraEntity` 或直接在最前面把 `Camera.entity` 临时设成喷火龙 —— **不建议现在做**。
- **区块加载**：镜头跑远后，客户端只保证玩家周围有区块，会看到空白地形。Cobblemon 自己也有"镜头中心强制加载区块"的需求（任务书第 4 节），那是后续 M1 的事。

### 6.3 实现建议

`GodMode` 用一个 static 字段存 `Vec3 cameraPos`，每 tick 由客户端根据 WASD/滚轮更新（M0.5 可以先固定"玩家头顶后方 8 格"，只验证"镜头能脱身"）。

## 7. 右键点地面 → 服务端执行

### 7.1 自定义包（1.21.1 / Fabric API）

1.21.1 用的是 **`CustomPacketPayload` + `PayloadTypeRegistry` + Fabric Networking**，Cobblemon 内部走它自己的 `CobblemonNetwork`/`PacketRegistrar`（Architectury 风格），**我们不要复用它的包系统**，直接用 Fabric 的原生写法，互相独立。**【源码·部分】** 我在 `common/.../net` 下没 grep 到 `CustomPayload`（Cobblemon 自建了一套），所以结论是"别碰它的网络层"。【推断】这部分 Fabric API 的签名在本轮没有本地文档可查，按 1.21.1 通行 API 给出。

**服务端侧注册：**
```java
public record MoveOrderPayload(BlockPos target) implements CustomPacketPayload {
    public static final Type<MoveOrderPayload> TYPE = new Type<>(Identifier.of("mymod", "move_order"));
    public static final StreamCodec<FriendlyByteBuf, MoveOrderPayload> CODEC =
        CustomPacketPayload.codec(MoveOrderPayload::write, MoveOrderPayload::new);

    private MoveOrderPayload(FriendlyByteBuf buf) { this(buf.readBlockPos()); }
    private void write(FriendlyByteBuf buf) { buf.writeBlockPos(target); }
    @Override public Type<? extends CustomPacketPayload> type() { return TYPE; }
}

// 初始化时
PayloadTypeRegistry.playC2S().register(MoveOrderPayload.TYPE, MoveOrderPayload.CODEC);
ServerPlayNetworking.registerGlobalReceiver(MoveOrderPayload.TYPE, (payload, context) -> {
    ServerPlayer player = context.player();
    context.server().execute(() -> {
        // 校验：玩家在上帝视角、目标点在 32 格内、该玩家有激活的喷火龙
        GodModeService.moveCharizardTo(player, payload.target());
    });
});
```

**客户端发送：**
```java
PayloadTypeRegistry.playC2S()  // 客户端不需要注册 C2S 的接收，只要 codec 一致
ClientPlayNetworking.send(new MoveOrderPayload(targetPos));
```
（`playC2S` 的 codec 注册是全局的：客户端要能编码，服务端要能解码，通常**两端初始化都注册**一次。**【推断】**）

### 7.2 把右键从"使用物品"改成"下指令"

最小可行做法：**Mixin `MouseHandler`**（Cobblemon 自己就有 `client/MouseHandlerMixin.java`，说明这条路可行）。

```java
@Mixin(MouseHandler.class)
public class MouseHandlerMixin {
    @Inject(method = "onPress", at = @At("HEAD"), cancellable = true)
    private void mymod$interceptRightClick(long window, int button, int action, int modifiers, CallbackInfo ci) {
        if (button != GLFW.GLFW_MOUSE_BUTTON_RIGHT) return;
        if (action != GLFW.GLFW_PRESS) return;
        if (!GodMode.active()) return;
        if (Minecraft.getInstance().screen != null) return;   // 有 GUI 时不拦
        GodMode.requestGroundClick();                          // 客户端射线打到地面再发包
        ci.cancel();                                           // 关键：吃掉这次右键
    }
}
```
**【未知】** `MouseHandler.onPress` 的准确签名在 1.21.1 是 `private void onPress(long window, int button, int action, int mods)`（mixin 需要 `@Inject` 到 `onPress` 或 `onRightClick`）。Cobblemon 的 `MouseHandlerMixin.java` 里有现成写法，**实现前先打开它照抄注入点**（本轮时间盒内没来得及读）。

**射线取点**：`Minecraft.player.pick(attackRange, partialTick, false)` 或 `level.clip(new ClipContext(...))`，拿到 `BlockHitResult` 的 `getBlockPos()`；没打到方块就取 `origin + direction * 32`。

**或者完全不 mixin 的降级方案**（如果右键拦截有坑）：用 `ClientTickEvents.END_CLIENT_TICK` 检测 `mc.options.keyUse.isDown()` 的上升沿 + 自己 raycast，只标记"下指令"但**不阻止原版使用物品**。副作用：会真的挥手/放方块/吃东西。M0.5 里玩家手里最好强制空手/不拿可放置物品来规避。

### 7.3 完整链路

```
右键按下 → MouseHandlerMixin cancel（前提：GodMode.active）
        → 客户端 raycast 得到 BlockPos
        → ClientPlayNetworking.send(MoveOrderPayload)
        → ServerPlayNetworking 接收（校验视角标记/距离/目标是否加载）
        → GodModeService 记下 (player uuid → target pos + active charizard uuid)
        → 服务端每 tick 推喷火龙（第 4 节）
```

**服务端权威校验必须有**：服务端不能相信客户端说"我在上帝视角"，要维护自己的 `Map<UUID, GodModeSession>`，进入/退出上帝视角也要发包告知服务端。**【设计建议】** 否则任何客户端都能指挥别人的宝可梦。

## 8. 锁定玩家本体

三条路，按"副作用从小到大"排：

| 方案 | 做法 | 副作用 | 推荐 |
|---|---|---|---|
| A. 客户端取消输入 | `ClientTickEvents` 里把 `player.input` 的 `forward/strafe/jumping/use/attack` 清零（或 mixin `LocalPlayer.aiStep`） | 只防"主动操作"；**防不住击退、爆炸、水流、传送**；服务端仍认为你在动，容易橡皮筋 | 只作辅助 |
| B. 服务端每 tick 归零速度 + 回写坐标 | `player.deltaMovement = Vec3.ZERO; player.hurtMarked = true; player.teleportTo(lockPos)`（每 tick 强制） | **最稳**；但会打断正常传送/载具/床，且 `teleportTo` 每 tick 发包开销大、客户端会抖 | **M0.5 推荐主方案**（只锁 x/z，保留 y 让人站地上；用 `setPos` 而不是每 tick `teleportTo`，5 tick 校正一次） |
| C. 直接 `player.setNoActionTime` / 附加 `noGravity` 等 | —— | 不管用，不解决移动 | 不采用 |

**推荐组合**：B 为主（每 tick 服务端把 x/z 拉回锁定点、清零水平速度，y 不动），A 为辅（客户端同时清输入，减少拉扯）。
**关键坑**：服务端 `setPos` 后必须 `hurtMarked=true`（或 `ServerPlayer.connection.teleport`）才能让客户端认可位置，否则客户端会"漂回去"。**【推断】**

## 9. 分步实施清单（目标：最快看到"喷火龙站在我面前"）

> 每一步都以"能看到/能验证"为终点，不要一次写全。

1. **空模组能加载**（30 分钟）
   - Fabric 模组骨架 + `fabric.mod.json` + 主类；`depends` 里加 cobblemon。
   - 验证：游戏能进、日志有我们 mod 的 init 行。
2. **`/charizard` 命令生成一只**（1 小时，**不碰镜头**）
   - 命令在玩家位置前方 3 格 `sendOut`，`mutation` 里设 `ownerUUID`、`isNoAi=true`。
   - 验证：喷火龙出现在面前、有模型有贴图、不动。**这一步过了，M0.5 的硬骨头就没了。**
   - 如果看不到：先查 species 是否解析成功、`sendOut` 返回值是否 null、实体是否被立即 `discard`。
3. **让它走**（1 小时）
   - 临时用命令 `/movecharizard x y z` 触发服务端每 tick 推行（第 4.2 节）。
   - 验证：走过去、动画切换到 walk、停下切回 idle。若播的是 walk 但位移为 0，说明用了 `setDeltaMovement` 而没 `move()`。
4. **F12 进上帝视角**（1 小时）
   - 先做"镜头固定到玩家上方 8 格、只改位置不改朝向"（第 6 节）。
   - 验证：镜头脱离身体，转向仍跟鼠标。
5. **右键下指令**（1.5 小时）
   - `MouseHandler` mixin + 发包 + 服务端接收（第 7 节）。
   - 验证：右键地面 → 喷火龙走过去；右键天空不崩、点击 GUI 不误触。
6. **锁定玩家本体**（0.5 小时）
   - 第 8 节方案 B + A。
   - 验证：镜头移动时玩家不跟着走、不被右键物品干扰。
7. **收尾**：退出上帝视角后镜头/玩家/喷火龙状态复原（M0.5 只需"喷火龙留在原地静立"）。

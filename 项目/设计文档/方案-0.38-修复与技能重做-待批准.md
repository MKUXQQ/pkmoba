## 2. 问题二：普通宝可梦移动太慢（含"迂回"残留）

### 2.1 根因 A：直线行走的判定恒为 false（确定性 Bug）

`项目\pkmoba\src\main\java\com\pkmoba\move\MoveOrderService.java:229-241`：

```java
var feet = new AABB(-width, -0.2, -width, width, 1.4, width).move(entity.position());
...
return level.noCollision(entity, feet);
```

`entity.position()` 是**脚底**。`-0.2` 意味着探测盒有 0.2 格埋在地面方块里 → `noCollision` **恒为 false** → `canStep` 恒 false → `straightWalk` 恒 false。

后果链：

1. `tickEntity` 每 tick 都走到 `:180` 的 `entity.getNavigation().moveTo(..., NAV_SPEED)`；
2. `NAV_SPEED = 1.2`（`MoveOrderService.java:36`）只是**寻路速度倍率**，不是格/秒；
3. 真实速度 = Cobblemon `PokemonEntity` 的 `MOVEMENT_SPEED` 属性 × 1.2，而该属性由种族速度值算出，普通宝可梦普遍很低；
4. 你写的"直线 0.32 格/tick（≈6.4 格/秒）"那套**一次都没跑过**。

这也解释了"还是慢" —— 上一轮的加速改动实际未生效。

### 2.2 根因 B：A* 节点链的微修正（残余"迂回"）

A* 返回的是方块中心节点链，相邻节点中心不共线，`LookControl`/寻路会按 4 方向微调 → 肉眼看到"走一步歪一下"。原 `ARRIVE_DISTANCE = 0.5`（`:35`）也偏严，靠近目标时会绕小圈。

### 2.3 修复方案

**A. 修正探测盒（1 行级改动）**

```java
// 从脚底 +0.02 起算，绝不埋进地面；高度 1.4 覆盖身体
var feet = new AABB(-width, 0.02, -width, width, 1.4, width).move(entity.position());
```

并补一条"支持面"检查（不是用碰撞盒判，而是用 clip 找地面）：

```java
// 从 position 下方 0.6 到上方 1.1 做竖直 clip，找到的地面高度差必须 ≤ STEP_UP
double ground = groundBelow(level, entity, pos.add(probe));
if (!Double.isFinite(ground) || ground - entity.getY() > STEP_UP) return false; // 悬空/高墙
```

**B. 显式限速（不再依赖 Cobblemon 属性）**

新增常量与算法，替换 `STEP_SPEED = 0.32`：

```java
/** 目标行走速度（格/tick）。0.23 ≈ 4.6 格/秒，介于玩家走路 4.3 与疾跑 5.6 之间。 */
private static final double WALK_SPEED = 0.23;
private static final double SPRINT_SPEED = 0.28;
```

- 每 tick 步长固定按 `WALK_SPEED`，由 `entity.move(MoverType.SELF, motion)` 直接驱动，**完全绕开** `MOVEMENT_SPEED` 属性；
- 若按住疾跑键（或距离 > 12 格自动加速）用 `SPRINT_SPEED`；
- 按物种微调（这是**建议值**，等你拍板）：水箭龟 ×0.9、喷火龙 ×1.15、其余 ×1.0。

**C. A* 只做兜底，且兜底时同步提速**

`canStep` 失败才寻路，并把倍率按属性反算，保证 A* 与直线速度一致：

```java
double attr = entity.getAttributeValue(Attributes.MOVEMENT_SPEED);
double navSpeed = attr <= 1.0E-4 ? 1.2 : (WALK_SPEED * 20.0 / attr);
entity.getNavigation().moveTo(x, y, z, Mth.clamp(navSpeed, 0.8, 3.0));
```

**D. 到达阈值** `0.5 → 0.6`，并保留"到达即停、不补走"。

### 2.4 验收

- 点 10 格外平地：到达耗时 = 距离 /（4.6 格/秒）±10%，身体行进方向与点到点连线夹角 < 10°。
- 点台阶/斜坡：能上，且不出现"左右摆头找路"。
- 点墙后：A* 绕行，绕行期间速度不下降。

## 3. 问题三：模型头乱晃

### 3.1 根因：4 个写者每 tick 抢写朝向，且每 tick 强制发包

| 位置 | 行为 |
|---|---|
| `move\MoveOrderService.java:263-266` | `setYRot` + `setYHeadRot` + `setYBodyRot` + `hurtMarked = true` |
| `combat\BasicAttack.java:256-257` | 每次开炮 `setYRot` + `setYHeadRot` |
| `combat\CharizardCombat.java:452-455` | 引导技能每 tick 转 18° 后写三件套 + `hurtMarked` |
| `combat\BlastoiseCombat.java:255-258`（旋转）与 `:266-269`（瞄准） | 同上 |

再叠加原版 `Mob.aiStep → LookControl.tick()` 每 tick 也会写 `YHeadRot`。**同一 tick 内多个写者以不同速率改同一个角度**，客户端在两次插值（`yRotO → yRot`）之间反复被重置，观感就是头在抖/乱晃。

`hurtMarked = true` 每 tick 置位还会让服务端**每 tick 强制同步速度包**，进一步加剧抖动。

### 3.2 修复方案

**A. 新增单一朝向仲裁 `combat\FacingService.java`**

```java
public final class FacingService {
    public enum Priority { CHANNEL(3), ATTACK(2), MOVE(1), NONE(0); }
    // 每 tick 只允许最高优先级的一个来源写朝向；同一 tick 内重复调用被忽略
    public static void request(PokemonEntity e, Priority p, Vec3 dir, float maxStep);
    public static void tickReset(MinecraftServer server); // ServerTickEvents.END_SERVER_TICK 清账
}
```

调用点改为 `FacingService.request(...)`，不再直接写 `setYRot`。

**B. 只写 yaw，且限速 15°/tick**

- 写 `setYRot(next)` + `setYHeadRot(next)`；
- **不写** `setYBodyRot`（交给原版 `LivingEntity.tickHeadTurn` 推导，避免身体/头两套值打架）；
- `TURN_PER_TICK` 统一 15（现在 18/22/瞬时三种混用）。

**C. 删除所有每 tick `hurtMarked = true`**

保留规则：仅当 `|Δyaw| > 25°` 或每 10 tick 一次时置 `hurtMarked = true`（保证远距离转向客户端能及时看到）。

**D. 移动时压制 LookControl**

在 `MoveOrderService` 的移动分支里，先 `entity.getLookControl().setLookAt(Vec3.atCenterOf(目标))` 交给我们自己，或在写朝向后立刻 `entity.setYHeadRot(entity.getYRot())` 确保同 tick 最后写者是仲裁器（Java 里后写覆盖，顺序固定即可）。

**E. 旋转技能期间头随身体**

`BlastoiseCombat.tickSpin` 不再单独改头，锁定 `YHeadRot = YRot`。

### 3.3 验收

- 平地移动 20 秒：截图/录像里头部相对身体无 ±5° 以上高频摆动。
- 原地按技能转向：头是"平滑转到"，不是"瞬间跳变"。
- 旋转技能期间：头不出现与身体反向的偏移。

## 4. 问题四：技能方向回到鼠标

### 4.1 冲突澄清（这是关键，需要你确认）

- m00118 你说："**喷射火焰跟随模型**，不是跟随鼠标，水炮也一样。"
- m00488 你说："我需要就**直接看我鼠标点击的方向**。"

我的理解（**请确认**）：你要的是两件事同时成立 ——

| 要素 | 归属 |
|---|---|
| 弹道/特效的**方向** | 鼠标点击（指向）的世界点 |
| 弹道/特效的**出源** | 模型嘴部/炮口，随模型移动而移动 |
| 模型自身朝向 | 施放当帧对齐到该方向（所以"看着像从模型喷出去"） |

即：**方向看鼠标、出源绑模型、模型当帧转向对齐**。上一轮我把"方向"也改成了模型正前方，这是过头了。

### 4.2 修复方案

**A. 撤回方向源**

`CharizardCombat.modelForward(...)` 保留（仍有用：鼠标指向天空时的退化方向），但**不再作为技能方向源**。

改为：

```java
/** 技能方向：优先鼠标世界点，退化到模型正前方。返回归一化水平方向。 */
public static Vec3 aimDirection(PokemonEntity e, @Nullable Vec3 aimPoint) {
    if (aimPoint == null) return modelForward(e);
    Vec3 origin = muzzle(e);            // 嘴/炮口，见 B
    Vec3 d = aimPoint.subtract(origin);
    if (d.horizontalDistanceSqr() < 1.0E-4) return modelForward(e);
    return new Vec3(d.x, 0, d.z).normalize();
}
```

**B. 出源统一走"模型嘴/炮口"（跟随模型）**

```java
/** 出源 = 身体 + 朝上 0.8×身高 + 正前方 0.425。模型移动，出源跟着移动。 */
public static Vec3 muzzle(PokemonEntity e) {
    return e.position()
            .add(0, e.getBbHeight() * 0.8, 0)
            .add(modelForward(e).scale(0.425));
}
```

**C. 服务端改回读 `aim`**

- `SkillCastPayload` 已携带 aim 世界点（客户端 `SkillKeys.fire()` 已发），**协议不用改**；
- `CharizardCombat` 的 Q 锥形/扇形、R 弹道：方向改回 `st.channelAim`（引导期）与 `payload.aim`（瞬时）；
- `BlastoiseCombat` 的 `W/E/R`：方向改回 `aimDirection(entity, aim)`；
- 每帧 `AimPayload`（2 tick 一次）继续用，引导类技能跟随鼠标实时转向。

**D. 模型当帧对齐**

施放瞬间调用 `FacingService.request(entity, ATTACK, aimDir, 180)` —— 允许一帧内转到位（`maxStep = 180`），避免"打完才慢慢转过来"。

### 4.3 验收

- 鼠标指向 A 点、模型在 B 点：技能从模型嘴部射向 A 点方向。
- 模型一边走一边喷火：火焰根部始终贴着嘴，不脱离、不留在原地。
- 鼠标指天空：技能朝模型正前方。

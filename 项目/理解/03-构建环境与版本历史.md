### 1.6 路径漂移（F:\deepseek\项目 → D:\dsh项目\宝可梦项目）的影响

实测（本次）：
```
Test-Path 'F:\jdk21m'  -> False
Test-Path 'F:\deepseek' -> False
Test-Path '项目\pkmoba\.git' -> False
Get-Command java -> C:\Program Files\Common Files\Oracle\Java\javapath\java.exe (java version "21.0.11")
$env:JAVA_HOME = ''   $env:GRADLE_USER_HOME = ''
```

逐项判断【推断，未运行构建】：
1. **直接构建会失败**：`org.gradle.java.home=F:/jdk21m` 指向不存在的目录，Gradle 在读取 properties 阶段就会报 “Java home supplied is invalid / Value 'F:/jdk21m' given for org.gradle.java.home Gradle property is invalid”。这是第一道、且必然触发的墙。
2. 改用 `项目\tools\jdk21` 可满足要求（Temurin 21.0.12.1，见 §2.1）；本机系统 Java 也是 21.0.11，但工程配置会优先覆盖它。
3. 依赖缓存不在默认位置：`项目\tools\gradle-home` 是独立 GRADLE_USER_HOME（wrapper dists/caches/modules-2/fabric-loom 都在里面），但没有任何机制自动指过去（环境变量为空、脚本里也没有）。不显式设 `GRADLE_USER_HOME=项目\tools\gradle-home` 就会去 `~/.gradle` 重新下载，等于联网重建缓存。
4. 工程本身**没有**写死 F: 的路径（build.gradle 全用相对路径 + 远程 maven 坐标），所以漂移只卡在 `org.gradle.java.home` 一处。Gradle/Loom 的下载缓存里如果带旧路径，最多触发重新下载，不影响可构建性。
5. `项目\pkmoba\build\libs` 里已有全部 33 个版本的 jar，`:jar`/`:remapJar` 的增量缓存也跨路径失效，但重新构建不依赖它。
6. 结论：**当前 D: 路径下“改一处 java.home + 设 GRADLE_USER_HOME 就能构建”的判断成立，但本次按规则没有真跑构建，属于未实测结论**。同时注意：旧证据只覆盖 F: 路径，发布 jar 的“可复现性”同样没有在 D: 上被实测过。

### 1.7 编码问题（客观缺陷）

- `build.gradle` / `gradle.properties` 的中文注释在字节层已是坏的：`build.gradle` 内含 U+FFFD（替换字符），本次用 Python 尝试 `utf-8 → cp936 → utf-8` 恢复时在 position 64 报 `UnicodeEncodeError: 'gbk' codec can't encode character '\ufffd'` → **已不可恢复**。事实内容仍可 100% 从代码结构读出（版本号、坐标、插件），只是注释文字丢失。
- `项目\README.md`、`项目\产物\M0.5\README.md`、`项目\协作\*.md` 的中文呈乱码（UTF-8→GBK→UTF-8 双重转码特征）；README.md 实测无法用 `encode('cp936').decode('utf-8')` 简单还原（`'utf-8' codec can't decode byte 0xcf in position 2`）。
- 而 `项目\设计文档\*.md`（如 `决策与环境记录-v1.md`）中文正常。→ 损坏集中在部分文件，非全局编码设置问题，属历史写入过程事故。
- 影响：任何自动化脚本/后续 agent 若按中文关键字 grep 这些文件会漏检；建议后续统一以 UTF-8 重写（本次只读，未改）。
